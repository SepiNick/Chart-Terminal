# طراحی چندکاربره: حالت‌های سرور PUBLIC و PRIVATE

وضعیت: فقط طراحی (چیزی پیاده‌سازی نشده). بر اساس کد در تاریخ 2026-11-04 نوشته شده است.
انتخاب‌گر: `CT_MODE=public|private` (پیش‌فرض `private`). حالت private همان رفتار امروز است، بایت به بایت.

ارجاع‌های خطی به شکل `file:line` و نسبت به پوشه‌ی `server/` هستند، مگر خلافش گفته شود. علامت «~» یعنی تقریبی.

---

## 0. یافته‌هایی که شکل همه‌چیز را تعیین می‌کنند

1. **دشمن، state سراسری است، نه SQL.** تقریباً هر ماژول ردیف‌هایش را هنگام import در یک `Map` سطح ماژول بار می‌کند (alerts در `alerts/index.ts:28`، brokers در `brokers/index.ts:~45`، forward، پیکربندی recorder) و تغییرات را با `broadcast()` سراسری (`core/http.ts:146`) به مجموعه‌ی سراسری `clients` (`core/http.ts:141`) می‌فرستد. هشت نقطه‌ی فراخوانی broadcast وجود دارد (alerts/index.ts:42,169؛ brokers/index.ts:97,143؛ forward.ts:75؛ notify/index.ts:290؛ state.ts:26,31). در یک سرور چندکاربره، هر هشت‌تای آن‌ها هشدارها، اعلان‌ها، حساب کاغذی و state یک کاربر را برای همه فاش می‌کنند. این محتمل‌ترین منبع نشت بین کاربران است.
2. **تنظیمات در جدول سراسری `config` هستند** (`core/db.ts:24`): `auth.password`، `notify.telegram/email/webhook`، `notify.vapid.public`، `lan` و `recorder`. این‌ها امروز در سطح سرورند و باید به تنظیمات سطح سرور و تنظیمات هر کاربر تقسیم شوند.
3. **کد کاربر داخل پردازه‌ی سرور اجرا می‌شود.** `src/mql/compiler/index.ts:42` و `src/ninja/compiler/index.ts:39` روی سورس کامپایل‌شده‌ی کاربر `new Function(...)` اجرا می‌کنند و Pine هم در همان استخر engine تفسیر می‌شود (`engine.ts:50`، `engineworker.ts`). یک worker thread محیط پردازه (`CT_SECRET_KEY`، فایل‌ها، شبکه، `import()` پویا) را مشترکاً در اختیار دارد و کدی که با `new Function` اجرا می‌شود می‌تواند `import('node:fs')` را صدا بزند. این یعنی اجرای کد از راه دور برای هر کاربر ثبت‌نام‌شده. **باید در حالت public خاموش باشد.** مهلت `RUN_TIMEOUT` (20 ثانیه) در `engine.ts` فقط CPU را محدود می‌کند، نه توانایی‌ها را.
4. **IP کلاینت همان آدرس socket است** (`core/auth.ts:53`). پشت Caddy/Docker هر درخواست از 127.0.0.1 یا IP پل شبکه می‌آید، پس محدودسازی به‌ازای IP و بررسی «راه‌اندازی فقط از localhost» (`authroutes.ts:18`) بی‌صدا از کار می‌افتد. مقدار `secure` برای listener از نوع HTTP به‌صورت ثابت `false` است (`index.ts:~25`، `http.ts:71`)، بنابراین پشت یک پروکسی TLS کوکی نشست هرگز `Secure` نمی‌گیرد. listener روی `127.0.0.1` قفل شده است (`index.ts:24`)، که برای پروکسی روی همان میزبان مناسب است ولی برای شبکه‌ی پل Docker نه.
5. **توزیع داده‌ی بازار از قبل مشترک است.** `market.ts:80` (نقشه‌ی `feeds` با کلید `exchange|symbol|tf`) و `core/bars.ts:28` (`series` با کلید `sym|tf`) چندین کلاینت را روی یک جریان بالادستی چندگانه می‌کنند. چیزی که کم است سقف‌هاست (به‌ازای هر socket، هر کاربر، و کل جریان‌های متمایز) و یک کش پاسخ REST برای `/api/bars`.
6. **کارگزارها امروز فقط testnet هستند** (فهرست مجاز `brokers/safety.ts`)، اما زیرساخت آن (کلیدهای API رمزنگاری‌شده در `secrets`، `broker_accounts`، سفارش‌های OCO/trailing شبیه‌سازی‌شده، حلقه‌ی polling) دقیقاً چیزی است که هرگز نباید روی میزبان public وجود داشته باشد، حتی برای testnet: یک سرور public نفوذشده کلیدها را در اختیار دارد و می‌توان آن را وادار به معامله کرد.
7. **لینک‌های اشتراک و رسانه مالک ندارند.** `GET /api/media/:id` و `DELETE /api/media/:id` (`media.ts:21,31`) و `DELETE /api/share/:id`، `GET /api/share`، `GET /api/share/layout/:id` (`share.ts:50-54`) فقط «لاگین بودن» را بررسی می‌کنند، نه مالکیت را. شناسه‌ها 128 بیت تصادفی‌اند، پس امروز فقط به‌خاطر غیرقابل‌حدس‌بودن امن است؛ در حالت چندکاربره این یک IDOR ذاتی است.

## 2. احراز هویت

### 2.1 مدل داده (`users.db`، فقط حالت public)

```
users(id INTEGER PRIMARY KEY, name TEXT NOT NULL UNIQUE COLLATE NOCASE, pw TEXT NOT NULL,
      role TEXT NOT NULL DEFAULT 'user',          -- 'admin' | 'user'
      status TEXT NOT NULL DEFAULT 'active',      -- 'active' | 'disabled'
      must_change INTEGER NOT NULL DEFAULT 0,     -- set after an admin reset
      created INTEGER, last_login INTEGER, invited_by INTEGER, quota TEXT /* JSON overrides */)
sessions(token_hash TEXT PRIMARY KEY, user_id INTEGER NOT NULL REFERENCES users ON DELETE CASCADE,
         created INTEGER, last_seen INTEGER, expires INTEGER, agent TEXT, ip TEXT)
invites(code_hash TEXT PRIMARY KEY, created_by INTEGER, uses_left INTEGER, expires INTEGER, note TEXT)
recovery_codes(user_id INTEGER, code_hash TEXT, used INTEGER DEFAULT 0, PRIMARY KEY (user_id, code_hash))
login_attempts(key TEXT PRIMARY KEY, n INTEGER, until INTEGER)     -- persisted so a restart does not reset a lockout
audit(id INTEGER PRIMARY KEY, at INTEGER, user_id INTEGER, ip TEXT, event TEXT)  -- login ok/fail, register, reset, delete, admin actions; capped
```

حالت private همان `config['auth.password']` و جدول `sessions` امروز را دست‌نخورده نگه می‌دارد؛ به `Ctx` یک `user = { id: 1, role: 'admin' }` مصنوعی داده می‌شود تا handlerها فقط یک بار و بر پایه‌ی `c.user` نوشته شوند.

### 2.2 ثبت‌نام (بدون زیرساخت ایمیل)

- `CT_REGISTRATION=invite|open|closed`، پیش‌فرض **invite** در حالت public.
- نام کاربری `^[a-z0-9_.-]{3,32}$` (یکتا بدون حساسیت به حروف)، نام‌های رزروشده مسدود هستند (`admin`، `root`، `system`...).
- گذرواژه: 10 تا 200 نویسه (سقف بالا جلوی DoS مبتنی بر scrypt را می‌گیرد)؛ اگر در فهرست همراه حدود 10 هزار گذرواژه‌ی رایج باشد یا برابر نام کاربری باشد رد می‌شود. بدون قاعده‌ی ترکیب نویسه.
- `POST /api/auth/register {name, password, invite?}`: کدهای دعوت 128 بیت تصادفی‌اند، به‌صورت هش‌شده با `uses_left` و `expires` ذخیره می‌شوند؛ ادمین آن‌ها را با CLI یا `POST /api/admin/invites` می‌سازد.
- در صورت موفقیت، پاسخ **8 کد بازیابی را یک بار** نشان می‌دهد (بخش 2.6) و کوکی نشست را تنظیم می‌کند.
- ثبت‌نام باز (اگر مالک اصرار کرد) حداقل به این‌ها نیاز دارد: سقف 3 ثبت‌نام در ساعت به‌ازای هر IP، سقف سراسری N کاربر جدید در روز، و اثبات کار به سبک hashcash (کلاینت یک پیشوند SHA-256 را حساب می‌کند، حدود 2 ثانیه)، چون CAPTCHA/ایمیل در دسترس نیست. پیش‌فرض همچنان فقط با دعوت است.
- پاسخ‌های یکنواخت و ثابت‌زمان برای ثبت‌نام ممکن نیست (نام کاربری اشغال‌شده دیده می‌شود)؛ این را بپذیرید ولی محدودسازی نرخ بگذارید.

### 2.3 هش‌کردن گذرواژه

scrypt (که از قبل در `core/auth.ts:17` هست، `node:crypto`، بدون وابستگی تازه) بماند، ولی:
- رشته‌ی خودتوصیف `scrypt$N$r$p$salt$hash` ذخیره شود (N=2^15، r=8، p=1، کلید 64 بایت، salt با 16 بایت) تا پارامترها بعداً قابل افزایش باشند و هش‌های قدیمی در ورود بعدی دوباره هش شوند.
- از `crypto.scrypt` **ناهمگام** با یک semaphore دو‌ظرفیتی استفاده شود. `scryptSync` فعلی (auth.ts:17,23) برای هر تلاش حدود 50 تا 100 میلی‌ثانیه event loop را قفل می‌کند، که روی سروری با socketهای زنده‌ی بازار، ورود را به یک DoS ساده تبدیل می‌کند.
- وقتی نام کاربری وجود ندارد هم همیشه یک scrypt با salt ساختگی اجرا شود (زمان‌ها یکسان می‌شود و شمارش کاربران ممکن نیست).
- مقایسه با `timingSafeEqual` (از قبل انجام می‌شود).

### 2.4 محدودسازی ورود

نقشه‌ی تک‌حافظه‌ای به‌ازای هر IP (`core/auth.ts:28-31`) با سه محدودیت مستقل که در `login_attempts` ذخیره می‌شوند جایگزین شود:
1. به‌ازای هر IP: 10 شکست در 10 دقیقه، سپس قفل نمایی تا 1 ساعت؛
2. به‌ازای هر جفت (حساب، IP): 5 شکست، نمایی؛
3. به‌ازای هر حساب (از هر IP): پس از 20 شکست در ساعت یک **تأخیر** اضافه شود (1 ثانیه به‌ازای هر تلاش اضافی، حداکثر 10 ثانیه)، قفل سخت نشود، وگرنه مهاجم قربانی را برای همیشه بیرون می‌اندازد.
به‌علاوه یک محدودکننده‌ی سراسری روی `POST /api/auth/*` (60 در دقیقه به‌ازای هر IP) و متن خطای یکنواخت «Wrong username or password».
IP کلاینت از یک helper پروکسی قابل‌اعتماد (3.4) می‌آید: `CT_TRUST_PROXY=1` فقط وقتی `X-Forwarded-For` را می‌خواند که همتای socket خود پروکسی باشد (loopback یا `CT_PROXY_IPS`)، و راست‌ترین گام غیرقابل‌اعتماد را برمی‌دارد. Caddy باید طوری تنظیم شود که هدر را بازنویسی کند، نه اینکه به آن اضافه کند.

### 2.5 نشست‌ها و کوکی‌ها

- توکن‌های مات 32 بایتی بمانند، با SHA-256 در حالت ذخیره هش شوند (`core/auth.ts:34-35`، همان‌طور که هست خوب است). `user_id` و یک `expires` مطلق (30 روز؛ بیکاری 14 روز) اضافه شود، به‌جای پنجره‌ی لغزان 60 روزه‌ی فعلی (`SESSION_DAYS`، auth.ts:~9).
- کوکی `__Host-ct_session; Secure; HttpOnly; SameSite=Strict; Path=/` در حالت public (به `Secure` نیاز دارد، پس به `X-Forwarded-Proto` قابل‌اعتماد هم). `sessionCookie` امروز (auth.ts:51) از قبل بقیه‌ی ویژگی‌ها را دارد.
- تغییر گذرواژه و ریست توسط ادمین همه‌ی نشست‌های همان کاربر را حذف می‌کنند (امروز: `DELETE FROM sessions`، auth.ts:18، همه‌ی کاربران). سقف 20 نشست به‌ازای هر کاربر؛ قدیمی‌ترین بیرون انداخته می‌شود.
- WebSocket: به `WsClient` فیلد `userId` داده شود (http.ts:137). هنگام خروج، غیرفعال‌شدن یا حذف، socketهای آن کاربر بسته شوند (`authroutes.ts:42-44` از قبل بر اساس شناسه‌ی نشست می‌بندد؛ به کاربر تعمیم داده شود).

### 2.6 چرخه‌ی عمر حساب

- **حذف حساب**: `DELETE /api/account {password}` ← حذف نشست‌ها، اشتراک‌های push، هشدارها از رجیستری حافظه، توقف watcherها، سپس `unlink` فایل DB کاربر (به‌همراه `-wal` و `-shm`)، حذف ردیف `users`، و نوشتن یک خط audit بدون محتوای شخصی. لینک‌های اشتراک با فایل از بین می‌روند. ادمین هم از طریق CLI می‌تواند انجامش دهد.
- **خروجی گرفتن از داده**: `GET /api/account/export` ← یک JSON (یا zip) از state، alerts، alert_log، تنظیمات notify (بدون endpointهای اشتراک)، رسانه‌ی ژورنال را stream می‌کند. پیاده‌سازی با فایل‌های جدا برای هر کاربر: `VACUUM INTO` به یک فایل موقت و سپس stream/سریال‌سازی؛ محدود به 1 بار در ساعت؛ با سقف حجم.
- **نقش ادمین**: ادمین اول خارج از مسیر عادی ساخته می‌شود، نه با رقابت روی `/register`: `CT_ADMIN=<name>` و در اولین راه‌اندازی سرور یک گذرواژه‌ی یک‌بارمصرف چاپ می‌کند (یا `node server/cli.ts create-admin <name>` که گذرواژه را می‌پرسد). ادمین می‌تواند کاربران را فهرست کند (نام، زمان ساخت، last_login، بایت‌ها)، غیرفعال/فعال کند، گذرواژه را ریست کند، حذف کند و دعوت‌نامه بسازد. ادمین **عمداً نمی‌تواند داده‌ی کاربر را بخواند** (بدون endpoint جعل هویت)؛ این باید در یادداشت حریم خصوصی رابط کاربری گفته شود. routeهای ادمین به نقش + وارد کردن دوباره‌ی گذرواژه‌ی ادمین (step-up) نیاز دارند + فقط با `Origin` هم‌سایت در دسترس‌اند.
- **بازنشانی گذرواژه بدون ایمیل**:
  1. *کدهای بازیابی*: 8 کد یک‌بارمصرف (هر کدام 80 بیت، یک بار هنگام ثبت‌نام نشان داده می‌شوند یا از تنظیمات دوباره تولید می‌شوند)، با scrypt هش‌شده؛ `POST /api/auth/recover {name, code, newPassword}` مثل ورود محدود می‌شود. مصرف یک کد همه‌ی نشست‌ها را خارج می‌کند و مجموعه‌ی تازه‌ای پیشنهاد می‌دهد.
  2. *ریست توسط ادمین*: CLI/endpoint یک گذرواژه‌ی موقت تصادفی تنظیم می‌کند که یک بار به ادمین نشان داده می‌شود، با `must_change=1`؛ کاربر پیش از هر API دیگر مجبور به صفحه‌ی تغییر گذرواژه می‌شود.
- **کاربران غیرفعال**: نشست‌ها در `sessionOf` رد می‌شوند، socketها بسته می‌شوند، ارزیابی هشدارها متوقف می‌شود.

### 2.7 CSRF، Origin، Host

- `sameOrigin()` (`core/http.ts:109-112`) درخواست‌های بدون `Origin` را می‌پذیرد (curl/تست‌ها). در حالت public، برای درخواست‌های غیر GET با نشست کوکی‌ای: لازم است میزبانِ `Origin` برابر `Host` باشد، **یا** `Sec-Fetch-Site: same-origin`، **و** هدر سفارشی `x-ct-client` هم الزامی است (کلاینت از قبل می‌فرستد، `src/sync.ts:api`)؛ یک فرم بین‌سایتی نمی‌تواند آن را تنظیم کند. `SameSite=Strict` به‌عنوان لایه‌ی دوم بماند. کلاینت‌های دارای توکن Bearer (اپ اندروید در آینده، بخش 5) از CSRF کوکی عبور می‌کنند ولی هرگز کوکی نمی‌گیرند.
- ارتقای WebSocket (`http.ts:150`): در حالت public `Origin` الزامی است (مرورگرها همیشه می‌فرستند).
- `allowedHost` (`http.ts:131`): در حالت public فقط `CT_ALLOWED_HOSTS` پذیرفته می‌شود (مجوز loopback و IP ماشین برداشته می‌شود، به‌جز مسیر healthcheck)، تا جلوی DNS-rebinding و ترفندهای هدر Host گرفته شود.
- هدرهای امنیتی: `Strict-Transport-Security` (از Caddy)، یک CSP برای پوسته‌ی اپ (`default-src 'self'; connect-src 'self' wss: https://data-api.binance.vision ...; img-src 'self' data: blob:`)، `Permissions-Policy` به `SECURITY_HEADERS` (`http.ts:54`) اضافه شود. `X-Frame-Options: DENY` از قبل هست.

## 3. جداسازی

### 3.1 مقایسه‌ی گزینه‌ها

**الف. ستون `user_id` + یک پوشش دسترسی به داده.**
+ یک فایل، یک پشتیبان، کوئری‌های ادمین بین‌کاربری و ترتیب ارزیابی هشدار ساده؛
- هر جدول و هر کوئری به `WHERE user_id = ?` نیاز دارد؛ یک شرط فراموش‌شده در هر جا (بیش از 70 route، `db.prepare` خام در 12 فایل) داده را نشت می‌دهد، آن هم بی‌صدا. تست‌ها باید نبودِ نشت را روی هر route اثبات کنند؛
- رجیستری‌های حافظه و `broadcast` هم همان بازنویسی را لازم دارند؛
- خروجی/حذف به‌ازای هر کاربر یعنی کپی‌های فیلترشده و بسیاری `DELETE ... WHERE user_id`؛
- نوشتن‌ها و checkpointهای WAL یک کاربر پرسروصدا بر همه اثر می‌گذارد؛ یک صفحه‌ی خراب کل را خراب می‌کند.

**ب. یک فایل SQLite برای هر کاربر** (`data/users/<id>.db`) + یک `users.db` مرکزی کوچک.
+ **جداسازی ذاتی**: handler فقط `c.db` کاربر خودش را می‌گیرد؛ فیلتر فراموش‌شده نمی‌تواند از کاربر عبور کند چون ردیف‌های دیگران در آن فایل نیستند. شناسه‌ی بیگانه صرفاً 404 می‌دهد. IDOR بین 70+ route برای همه‌ی داده‌های مبتنی بر SQL منتفی می‌شود؛
+ خروجی = یک `VACUUM INTO`؛ حذف = unlink؛ سهمیه = اندازه‌ی فایل (به‌علاوه `PRAGMA max_page_count` به‌عنوان سقف سخت)؛
+ هیچ تغییر schema در جدول‌های ماژول‌های موجود (بدون ستون `user_id`، بدون مهاجرت DB حالت private: فایل `chart-terminal.db` در حالت private *همان* فایل کاربر 1 است)؛
+ خرابی‌ها و نوشتن‌ها جدا می‌مانند؛ WAL برای هر فایل؛
- دسته‌های باز زیاد: از یک LRU با حداکثر حدود 64 `DatabaseSync` استفاده کنید که بعد از 5 دقیقه بی‌کاری بسته می‌شوند؛ باز کردن + مهاجرت به‌صورت تنبل (فهرست هر مهاجرت کوچک است)؛
- کارهای بین‌کاربری (ارزیابی هشدار، fan-out ‏push) باید روی کاربران پیمایش کنند: راه‌حل یک رجیستری حافظه که هنگام boot از یک اشاره‌ی کوچک `users.has_active_alerts` بار می‌شود و به‌صورت تنبل پر می‌شود؛
- پشتیبان‌ها N فایل‌اند (حلقه‌ی شبانه‌ی `VACUUM INTO` یا Litestream به‌ازای هر فایل)؛ برای صدها تا چند هزار کاربر قابل‌قبول است، بعد از حدود 10 هزار باید بازبینی شود.

**توصیه: ب.** دلیل تعیین‌کننده، سطح 100+ route / 12 فایل با importهای `db` سطح ماژول است: ب عبارت «یادت باشد در هر کوئری فیلتر کنی» را به «راهی برای رسیدن به ردیف‌های کاربر دیگر وجود ندارد» تبدیل می‌کند، که تنها ویژگی‌ای است که در برابر ویرایش‌های آینده دوام می‌آورد. سطح نشت بین‌کاربری باقی‌مانده لایه‌ی حافظه و WebSocketهاست که هر دو گزینه به‌هرحال باید درستش کنند (3.2). یک تست/lint نگه دارید که هیچ ماژولی خارج از `core/` مستقیماً `db` را import نکند.

### 3.2 سازوکار

1. `core/db.ts` برای حالت private همچنان `db` (DB تکی) را export می‌کند و `userDb(id): DatabaseSync` اضافه می‌کند (LRU؛ همه‌ی مهاجرت‌های ثبت‌شده را به‌صورت تنبل اعمال می‌کند؛ `DATA_DIR/users/<id>.db`). `migration(name, sql)` امروز هنگام import یک بار روی تنها DB اجرا می‌شود (`db.ts:16-21`)؛ آن را عوض کنید تا `(name, sql, scope: 'user'|'central')` را *ثبت* کند و هنگام باز شدن اجرا شود. حالت private آن‌ها را فوراً روی همان DB تکی دقیقاً مثل امروز اجرا می‌کند.
2. `Ctx` (`core/http.ts:15`) فیلدهای `user: { id, name, role }` و `db: DatabaseSync` را می‌گیرد. دروازه‌ی احراز هویت (`http.ts:82`) آن‌ها را پر می‌کند. handlerها از `c.db` استفاده می‌کنند، هرگز از `db` سطح ماژول. آن‌گاه TypeScript هر ماژول تبدیل‌نشده را علامت می‌زند (مرحله‌ی کامپایل `tsc --noEmit` از قبل در `npm run build` هست).
3. `WsClient` فیلد `userId` می‌گیرد؛ `broadcast(msg, except)` ← `broadcastTo(userId, msg, except?)`. نام قدیمی حذف می‌شود تا هر 8 نقطه‌ی فراخوانی تا وقتی کاربر نگیرند کامپایل نشوند (شبکه‌ی ایمنی ارزان و مکانیکی).
4. رجیستری‌های حافظه به‌ازای هر کاربر: `alerts: Map<userId, Map<id, Alert>>`، `states` با کلید `(userId,id)`. watcherهای هشدار بر اساس `(sym,tf)` مشترک می‌مانند (`alerts/index.ts:52-59`) با یک نمایه‌ی معکوس به مالکان.
5. کار پس‌زمینه‌ای که درخواستی ندارد (شلیک هشدار، push) با `withUser(id, fn)` به `db` و مقصد broadcast می‌رسد.
6. تست lint: grep که `from '../core/db.ts'` فقط در `core/`، `users/` و CLI دیده شود.

### 3.3 برنامه‌ی تست جداسازی

- `server/isolation.test.ts` (node:test، درون‌پردازه‌ای، `CT_MODE=public`، `CT_DATA_DIR` موقت، `CT_NO_AUTOSTART=1`):
  1. کاربران A و B را ثبت‌نام کنید (با دعوت)، هر دو را لاگین کنید (cookie jar جدا)؛
  2. به‌عنوان A از هر چیز یکی بسازید: کلیدهای state، alert، اشتراک push، media، snapshot اشتراک + layout، تنظیمات notify؛
  3. **همه‌ی routeهای ثبت‌شده** را از router فهرست کنید (آرایه‌ی `routes` در بیلدهای تست در دسترس باشد) و به‌عنوان B با شناسه‌های A و با گونه‌های فهرست/کوئری صدایشان بزنید؛ تأیید کنید بدنه‌ی پاسخ هیچ‌یک از رشته‌های نشانه‌ی A را ندارد (در هر مقدار ذخیره‌شده نشانه‌های یکتا مثل `A-SECRET-<random>` بگذارید) و routeهای مبتنی بر شناسه 404 می‌دهند، نه 200 یا 403 (403 وجود را فاش می‌کند)؛
  4. WebSocket: A و B را وصل کنید، به‌عنوان A تغییر بدهید، تأیید کنید B هیچ فریمی حاوی نشانه دریافت نمی‌کند (`broadcast` را پوشش می‌دهد)؛
  5. فهرست مسدود حالت public: تأیید کنید `/api/broker/*`، `/api/forward*`، `/api/ml/*`، `/api/ai/*`، `/api/lan`، `/ca.crt`، PUT روی `/api/recorder`، `/api/notify/telegram/chats` همه 404 می‌دهند (route وجود ندارد، نه فقط ممنوع) و `POST /api/alerts` با `kind:'script'` پاسخ 400 می‌دهد؛
  6. نگهبان پوشش route: اگر routeای وجود داشته باشد که جدول تست آن را طبقه‌بندی نکرده (U/G/X/auth) تست شکست بخورد، تا routeهای جدید بدون بازبینی ارسال نشوند؛
  7. حذف: A را حذف کنید، تأیید کنید فایل رفته، کوکی A رد می‌شود، لینک اشتراک A به 404 می‌رسد و B تحت تأثیر نیست؛
  8. نشست: B نمی‌تواند نشست‌های A را فهرست یا حذف کند (`/api/auth/sessions`).
- گونه‌ی fuzz: شناسه‌های تصادفی، path traversal در `:key`، بدنه‌های بیش‌ازحد بزرگ، عدم تطابق `Content-Type`.

### 3.4 دروازه‌ی حالت و اعتماد به پروکسی (کلید `CT_MODE`)

- `server/core/mode.ts`: `export const MODE = process.env.CT_MODE === 'public' ? 'public' : 'private'`؛ برای هر مقدار غیرخالی دیگر فوراً شکست بخورد.
- `index.ts`: importهای بی‌قیدوشرط (:4-21) با فهرست به‌ازای هر حالت جایگزین شود. حالت public ماژول‌های `brokers`، `forward`، `engine`، `recorder`، `llm`، `ml`، `lan`، `mt5` را **اصلاً import نمی‌کند**، پس مسیر کدی برای رسیدن وجود ندارد، نه فقط یک handler نگهبان‌دار. حالت public اگر `CT_SECRET_KEY` روی هر مقداری تنظیم باشد (کلیدها نباید وجود داشته باشند) یا اگر `server/data/secret.key` همراه با secretهای کارگزار موجود باشد، از راه‌اندازی خودداری می‌کند.
- listener در حالت public: `CT_HOST` (پیش‌فرض `127.0.0.1`، compose فقط داخل شبکه‌ی کانتینر آن را `0.0.0.0` می‌گذارد)، `CT_TRUST_PROXY`، `CT_PUBLIC_URL` (برای `secure`، کوکی `__Host-`، CORS و subject مربوط به VAPID).
- خودبررسی راه‌اندازی در public: با `CT_ALLOWED_HOSTS` خالی اجرا نمی‌شود، و تنظیم‌نبودن `NODE_ENV` هشدار می‌دهد.
- `/api/auth/status` مقدار `{ mode, registration, features: { brokers:false, ... } }` را اعلام می‌کند تا کلاینت خودش را وفق دهد (5).

## 4. سهمیه‌ها و کنترل سوءاستفاده

### 4.1 اجرای اسکریپت سمت سرور: **در حالت public غیرفعال شود**

پیشنهاد قطعی و مذاکره‌ناپذیر (یافته‌ی 0.3): نه engine pool، نه `forward`، نه هشدار `kind:'script'`، نه کامپایل MQL/Ninja روی سرور، نه `ml`. استراتژی‌ها، اندیکاتورها و بک‌تست‌های Pine/MQL/Ninja کاملاً در مرورگر کاربر کار می‌کنند (مفسّرها در `src/` هستند). اگر روزی هشدار اسکریپتی یا forward test سمت سرور لازم شد، حداقلِ sandbox قابل‌قبول این است: فقط Pine (خودِ مفسّر، نه `new Function`)، یک پروسه‌ی OS جدا برای هر گروه مستأجر بدون env، پرچم‌های `--permission` بدون دسترسی به fs و شبکه، محدودیت CPU/حافظه با cgroup (مثلاً `CPUQuota` در systemd)، 1 ثانیه برای هر اجرا و 2 اجرا در ثانیه برای هر کاربر. این خودش یک پروژه‌ی جداست؛ کار را با آن شروع نکنید.
کاربرانی که هشدار اسکریپتی یا forward test لازم دارند، سرور private را روی کامپیوتر خودشان اجرا می‌کنند و کلاینت را به آن وصل می‌کنند (5).

### 4.2 توزیع داده‌ی بازار برای 1000 کاربر

آنچه از قبل خوب کار می‌کند: یک فید بالادستی به‌ازای هر `(exchange,symbol,tf)` (`market.ts:80-118`)، یک سری بار به‌ازای هر `(sym,tf)` برای هشدارها (`core/bars.ts:28`)، نمونه‌های CCXT مشترک (`ccxt.ts:11`)، و derivs/macro/news کش‌شده (بخش 1.2 را ببینید).
آنچه باید اضافه شود:
1. **سقف سراسری برای فیدهای بالادستیِ متمایز**: مثلاً 300 فید کندل، 60 فید معاملات، 40 فید order-book (`market.ts:119-149`)؛ بعد از رسیدن به سقف، اشتراک جدید با `{type:'error', code:'feed_limit'}` رد می‌شود، مگر اینکه فید منطبقی از قبل وجود داشته باشد. فیدهای order-book و معاملات پرهزینه‌اند: در صورت نیاز آن‌ها را به کاربرانی با سنِ حساب مشخص یا پرچم ادمین محدود کنید.
2. **بستن فید بیکار با مهلت**: فیدها همین حالا وقتی `subs` خالی شود متوقف می‌شوند (`market.ts:~95`)؛ یک مهلت 20 ثانیه‌ای اضافه کنید تا قطع و وصل‌های پیاپی باعث چرخش سوکت‌های بالادستی نشود.
3. **کش REST و ادغام درخواست‌ها (coalescing)** برای `/api/bars` (`market.ts:~63`, `ccxt.ts:74`): کلید `(exchange,symbol,tf,until,limit)`، TTL برابر 5 ثانیه برای آخرین صفحه و 10 دقیقه برای صفحه‌های تاریخیِ `until`، اشتراک promiseهای در حال اجرا، LRU با 500 ورودی / 64 MB. همین کار برای `/api/tickers` (TTL برابر 3 ثانیه) و `/api/trades`.
4. **token bucket خروجی به‌ازای هر صرافی** که بین همه‌ی کاربران مشترک است (limiter داخلی CCXT به‌ازای هر نمونه است؛ سقف را حدود 60٪ از وزن مجاز منتشرشده‌ی صرافی بگذارید) همراه با صف منصفانه به‌ازای هر کاربر تا backfill یک کاربر بقیه را گرسنه نکند.
5. **تغذیه‌ی هشدارها از کلاین 1 دقیقه‌ای فقط یک بار به‌ازای هر نماد** و استخراج تایم‌فریم‌های بزرگ‌تر (کد همین حالا در `market.ts` با `emitAgg` تجمیع می‌کند)؛ امروز `streamBars` برای نمادهای ساده یک سوکت کلاین Binance به‌ازای هر `(sym,tf)` باز می‌کند (`src/data.ts:~128`)، یعنی 1000 کاربر × 10 هشدار می‌تواند هزاران سوکت بسازد. از streamهای ترکیبیِ Binance (`/stream?streams=`، تا 1024 stream در هر اتصال) و یک pool اتصال استفاده کنید.
6. **polling یاهو/FX** هر 15 ثانیه به‌ازای هر نماد (`market.ts:~97`): بر اساس نماد مشترک شود و به 100 نماد محدود شود.
7. معیارهای تعداد فیدها در `/api/admin/stats` (فقط ادمین) در دسترس باشد و هر دقیقه لاگ شود.

### 4.3 سایر مسیرهای سوءاستفاده

- `GET /api/alerts/log` و مشابه آن ارزان‌اند، اما `importLog` در هر فراخوانی 20,000 ردیف می‌پذیرد (alerts/index.ts:~196) و `PUT /api/state` تا 8 MB: سهمیه‌های بایتی این‌ها را پوشش می‌دهند.
- `/s/:id` عمومی است و از origin خودِ برنامه ارائه می‌شود؛ `nosniff` و CSP sandbox را نگه دارید (همین حالا هست) و ارائه‌ی تصاویر کاربران از یک origin جدا و بدون کوکی (`CT_SHARE_ORIGIN`) را در نظر بگیرید تا باگ content-sniffing نتواند سوار کوکی‌های origin برنامه شود.
- سطح SSRF خروجی در حالت public به endpointهای سرویس push کاهش می‌یابد. `notify_push_subs.endpoint` را کاربر می‌دهد و `web-push` آن را fetch می‌کند: https و یک allow-list از هاست‌های شناخته‌شده‌ی push را الزامی کنید (`fcm.googleapis.com`، `*.push.apple.com`، `*.notify.windows.com`، `updates.push.services.mozilla.com`، `*.push.services.mozilla.com`)؛ IP literal و هر چیز دیگر را رد کنید. (امروز فقط `https://` بررسی می‌شود، notify/index.ts:~197.)

## 5. کلاینت: دو سرور

### 5.1 مفاهیم

- **سرور همگام‌سازی (sync)** (`syncUrl`): حساب، state همگام‌شده، هشدارها و push را نگه می‌دارد. می‌تواند سرور public یا سرور private کاربر باشد. به‌طور پیش‌فرض برنامه از همین‌جا *ارائه می‌شود*.
- **سرور معاملاتی (trading)** (`tradeUrl`): اختیاری، **باید** سرور private خودِ کاربر یا `localhost` باشد؛ بروکرها، forward testها، recorder، LLM، MT5 و ML اینجا زندگی می‌کنند.
- سرور در حالت private هر دو نقش را دارد (تجربه‌ی تک‌سروریِ امروز پیش‌فرض می‌ماند و UI جدیدی نمی‌خواهد).

### 5.2 چه چیزی در `src/` تغییر می‌کند

- امروز همه‌ی فراخوانی‌ها هم‌مبدأ (same-origin) و نسبی‌اند (`api()` در `src/sync.ts`، و `fetch('/api/...')` خام در `boot.ts:11`، `journal/media.ts:21,44`، `ai/panel.ts:81`، `sync.ts:169`؛ سه سازنده‌ی WebSocket در `data.ts:74`، `orderflow/feed.ts:142`، `sync.ts:158` همگی از `location.host` استفاده می‌کنند). فایل `src/servers.ts` را معرفی کنید: `endpoints = { sync: {base, token?}, trade: {base, token?} }`، `apiSync(path)`، `apiTrade(path)`، `wsUrl('sync'|'trade')`؛ fetchهای خام (5 جا) و `new WebSocket` (3 جا) را با آن جایگزین کنید. `broker/remote.ts` (`RemoteBroker`، `call: Api = api`، :12-16) همین حالا تزریق‌پذیر است: آن را با `apiTrade` بسازید؛ `ai/panel.ts`، فراخواننده‌های `ml` و خواننده‌های `recorder` (`orderflow/source.ts`) هم همین‌طور.
- **احراز هویت بین originها**: کوکی‌های `SameSite=Strict` وقتی صفحه از سرور A ارائه می‌شود و به سرور B فراخوانی می‌زند کار نمی‌کنند. گزینه‌ها: (الف) صفحه همیشه توسط سرور *sync* ارائه شود و سرور trade فقط با `fetch` و `Authorization: Bearer <token>` (بدون کوکی) استفاده شود، با CORS در سرور trade که دقیقاً به origin صفحه محدود شده؛ (ب) کاربر برنامه را مستقیم از سرور trade باز کند. گزینه‌ی (الف) را انتخاب کنید: توکن‌های دستگاه را به حالت private اضافه کنید: `POST /api/auth/device {password}` ← یک توکن تصادفی بلندمدت (سمت سرور هش می‌شود، در فهرست sessionهای موجود قابل ابطال است). WS آن را به‌صورت اولین پیام `{op:'auth', token}` می‌فرستد (نه در URL تا در لاگ‌ها نیفتد). allow-list مربوط به CORS در سرور trade یک تنظیم است (`CT_CORS_ORIGINS`)، به‌طور پیش‌فرض خالی، پس برای کاربران فعلی هیچ چیز تغییر نمی‌کند.
- **Mixed content**: صفحه‌ای که روی HTTPS (public) ارائه می‌شود نمی‌تواند به `http://192.168.x.x` فراخوانی بزند. بنابراین سرور trade باید `https` باشد (روند CA شبکه‌ی محلی که همین حالا هست، `docs/lan-setup.md`) یا کاربر از طریق یک تونل (Tailscale/Cloudflare Tunnel) که HTTPS واقعی می‌دهد به آن برسد. `http://localhost` در مرورگرها مستثناست (secure context)، پس کاربر برنامه‌ی دسکتاپ روی همان کامپیوتر کار می‌کند؛ این را صریح مستند کنید. پوسته‌ی Electron دسکتاپ همچنان سرور بسته‌بندی‌شده‌ی خودش را بارگذاری می‌کند (same-origin) و می‌تواند برای برنامه‌ی وب سرور trade باشد.
- **هرگز اطلاعات معاملاتی را به سرور sync نفرستید**: `apiTrade` هیچ fallbackی به `apiSync` ندارد؛ اگر `tradeUrl` خالی باشد UI بروکر/forward/ML/AI پنهان می‌شود. یک unit test تضمین می‌کند که هیچ مسیری در کد `/api/broker` را از طریق کلاینت sync صدا نمی‌زند.

### 5.3 رابط کاربری

- **انتخاب‌گر سرور** در صفحه‌ی اول و در تنظیمات ← سرورها: فهرست سرورهای ذخیره‌شده `{name, url, role}`؛ «افزودن سرور» مسیر `GET /api/auth/status` را probe می‌کند (`mode`، `registration` و `features` را می‌گیرد) و به کاربر می‌گوید این چه نوع سروری است. فقط در `localStorage` ذخیره می‌شود (همگام نمی‌شود؛ مخصوص هر دستگاه است و توکن دارد).
- **صفحه‌های ثبت‌نام / ورود** (`src/login.ts`): `loginScreen` فقط‌رمزعبور را با نام کاربری + رمزعبور جایگزین کنید؛ «ساخت حساب» (با فیلد کد دعوت وقتی `registration:'invite'`)، نمایش کدهای بازیابی با چک‌باکس «ذخیره کردم»، «رمز را فراموش کرده‌اید؟ از کد بازیابی استفاده کنید»، و صفحه‌ی اجباریِ تغییر رمز را اضافه کنید. حالت private صفحه‌ی تک‌رمزی را نگه می‌دارد (status مقدار `mode:'private'` می‌دهد).
- **منوی حساب** (`login.ts:accountMenu`): گزینه‌ی «حساب‌های صرافی…» در سرورهای public پنهان شود؛ «خروجی گرفتن از داده‌هایم»، «حذف حسابم» و «کدهای بازیابی» اضافه شوند.
- **پنهان‌کردن UI معاملاتی در public**: وقتی `features.brokers === false` و سرور trade تنظیم نشده، پنل کناریِ حساب‌ها (`main.ts:795` `renderAccounts`، دکمه‌ی ریل `data-side="accts"`)، انتخاب‌گر بروکر در order-ticket (`main.ts:1007`؛ فقط بروکر Paper داخلی می‌ماند که کاملاً سمت کلاینت است و به‌صورت state با نام `acct` همگام می‌شود)، UI مربوط به Forward-test، پنل AI، ابزارهای ML، تنظیمات recorder و تنظیمات LAN پنهان می‌شوند.
- **توضیح دلیل**: یک اعلان یک‌باره و پیوند دائمی «چرا؟»: «این سرور عمومی هرگز کلید صرافی ذخیره نمی‌کند و سفارش ثبت نمی‌کند. برای معامله، سرور خودتان (کامپیوتر شخصی یا یک سرور خصوصی) را در تنظیمات ← سرور معاملاتی وصل کنید.» پیوندی کوتاه به `docs/headless-server.md` و یک راهنمای QR/URL اضافه کنید.
- **معاملات کاغذی (paper)** روی سرورهای public کاملاً قابل‌استفاده می‌ماند، چون state محلی است.
- **Android/PWA**: برنامه‌ی نصب‌شده به origin صفحه گره خورده است (`docs/android.md`)؛ کاربران یک origin را به‌عنوان خانه انتخاب می‌کنند. پشتیبانی از «خانه‌ی public + معاملات private» در PWA به 5.2(الف) با CORS تکیه دارد. یک پوسته‌ی بومی بعدی (Capacitor) می‌تواند هر دو URL را به‌صورت بومی نگه دارد.
- ساخت‌های `lite/` و `desktop/` در حالت `private` می‌مانند و تأثیری نمی‌پذیرند.

## 6. Web Push

- VAPID: یک جفت کلید به‌ازای هر **سرور** (نه هر کاربر). Web Push اشتراک را به کلید سرور برنامه گره می‌زند، پس کلید جدا برای هر کاربر ما را مجبور به اشتراک مجدد می‌کند و جداسازی بیشتری نمی‌دهد. `notify.vapid.public` / راز `push.vapid.private` (notify/index.ts:156-163) را نگه دارید ولی: حالت public از `CT_VAPID_PUBLIC`/`CT_VAPID_PRIVATE` می‌خواند (یا یک بار می‌سازد و در `users.db`/`secrets` ذخیره می‌کند)، و **هرگز خودکار بازتولید نمی‌کند**: کد فعلی وقتی هر یک از کلیدها نباشد همه‌ی اشتراک‌ها را پاک می‌کند (:~162). کلید گم‌شده باید با خطای بلند شکست بخورد.
- `vapidSubject()` (:~164) امروز از ایمیل پیکربندی SMTP کاربر استفاده می‌کند، وگرنه `chart-terminal@example.com`. از `CT_VAPID_SUBJECT` استفاده کنید (`mailto:` یا URL از نوع `https:` متعلق به اپراتور).
- اشتراک‌ها: جدول به‌ازای هر کاربر (در DB کاربر). `sendPush(n)` (:171) همه‌ی ردیف‌ها را کوئری می‌کند؛ آن را به `sendPush(n, userId)` تبدیل کنید که از DB همان کاربر استفاده کند. چون `endpoint` کلید اصلی است، اگر یک مرورگر زیر دو حساب مشترک شود (جابه‌جایی حساب)، در یک DB آخرین نویسنده برنده می‌شود، اما با فایل جدا برای هر کاربر ممکن است یک endpoint در فایل دو کاربر بماند و بعد از خروج/ورود جابه‌جاشده فرد اشتباه اعلان بگیرد. راه‌حل: جدول مرکزی `push_endpoints(endpoint PRIMARY KEY, user_id)` در `users.db`؛ اشتراک جدید endpoint را به کاربر جدید منتقل می‌کند و از فایل کاربر قبلی حذف می‌کند؛ خروج می‌تواند به‌طور اختیاری اشتراک را لغو کند.
- payloadها جز متن هشدار رازی ندارند؛ `data.url` فقط same-origin بماند (service worker همین را اعمال می‌کند، `public/sw.js`).
- سقف‌ها: 5 اشتراک برای هر کاربر، حذف با 404/410 (وجود دارد، :~180)، پاک‌سازی اشتراک‌هایی که 60 روز `last_ok` نداشته‌اند.
- توزیع: یک صف ارسال با هم‌زمانی سراسری 20 و محدودیت نرخ 4 برای هر کاربر؛ سرویس‌های push در سوءاستفاده 429 برمی‌گردانند، با jitter عقب‌نشینی کنید.
- Service worker: handler مربوط به `pushsubscriptionchange` «به کوکی نشست واردشده نیاز دارد» (انتهای sw.js)؛ در حالت چندکاربره این درست است، اما در worker چیز مخصوص کاربر را کش نکنید.
- حالت private: بدون تغییر، یک کاربر، جفت VAPID خودش.
- **push از سرور private برای برنامه‌ای که به سرور public وارد شده**: مرورگر به‌ازای هر scope سرویس‌ورکر یک اشتراک دارد و service worker به origin صفحه گره خورده است. اگر origin خانه سرور public باشد، push با کلید VAPID سرور public می‌آید؛ هشدارهایی که روی سرور private ارزیابی می‌شوند نمی‌توانند مستقیم push بزنند. دو طراحی: (i) هشدارهای سرور private فقط وقتی push می‌زنند که origin صفحه همان سرور private باشد؛ (ii) بعداً: سرور private هشدارهای فعال‌شده را به `POST /api/notify/relay`ِ احرازشده‌ی سرور public برای آن کاربر می‌فرستد (با توکن دستگاهی که کاربر می‌دهد) و آن سرور push می‌زند. ابتدا (i) را عرضه کنید و مستند کنید.

## 9. ده ریسک برتر یک سرور عمومی چندکاربره‌ی ترمینال معاملاتی

1. **نشت داده‌ی بین کاربران از طریق `broadcast`ِ سراسری WS و state سطح ماژول** (یافته‌ی 0.1). راهکار: handle مربوط به DB هر کاربر در `Ctx`، جایگزینی `broadcast` با `broadcastTo(userId,...)` (شکست در زمان کامپایل)، آزمون isolation مسیر/WS که هر مسیر را طبقه‌بندی می‌کند.
2. **اجرای کد از راه دور از طریق اسکریپت‌های کاربر سمت سرور** (`new Function` در کامپایلرها، 0.3). راهکار: engine، forward، هشدارهای اسکریپتی و ML در public import نمی‌شوند؛ آزمونی که نبودن این مسیرها را بررسی کند؛ کانتینر بدون راز، با rootfs فقط‌خواندنی و capabilityهای حذف‌شده.
3. **کلیدهای صرافی یا توان معامله روی هاست عمومی**. راهکار: ماژول brokers import نمی‌شود؛ `secretSet` نام‌های `broker:*` را رد می‌کند؛ راه‌اندازی با `CT_SECRET_KEY` یا فایل کلید رازِ موجود رد می‌شود؛ کلاینت هرگز فراخوانی‌های بروکر را به سرور sync نمی‌فرستد؛ مستندسازی مدل سرور معاملاتی.
4. **حمله‌ی اعتبارنامه: credential stuffing، brute force، شناسایی کاربر، سوءاستفاده از قفل حساب.** راهکار: throttling سه‌لایه در DB، خطاهای یکسان و scrypt ساختگی، scrypt ناهمگام با semaphore، بررسی رمزهای لو‌رفته/رایج، ثبت‌نام فقط با دعوت، audit log، سقف نشست به‌ازای هر کاربر.
5. **جعل پروکسی/IP و تنزل کوکی** (`clientIp` = آدرس سوکت، `secure=false`، 0.4). راهکار: `CT_TRUST_PROXY` همراه با تأیید peer، بازنویسی XFF توسط Caddy، کوکی `__Host-` با Secure، allow-list برای `Host`، HSTS.
6. **CSRF / ربایش WebSocket بین‌سایتی** (اجازه‌ی نبودن `Origin` در `http.ts:110`، WS در `http.ts:150`). راهکار: الزام `Origin` یا `Sec-Fetch-Site` به‌علاوه‌ی `x-ct-client` در درخواست‌های تغییردهنده، `SameSite=Strict`، الزام Origin در upgrade.
7. **SSRF و relay اسپم از طریق کانال‌های خروجی** (webhook، SMTP، Telegram، endpointهای دلخواه push، پروکسی‌های localhostِ LLM/MT5). راهکار: این کانال‌ها در public حذف می‌شوند؛ endpointهای push به هاست‌های شناخته‌شده‌ی سرویس push محدودند؛ هیچ fetch خروجی روی URL داده‌شده‌ی کاربر نیست؛ پروکسی loopback نیست.
8. **تخلیه‌ی منابع / DoS**: فیدها و هشدارهای نامحدود، بدنه‌های 8 تا 20 MB، scrypt هم‌گام، رشد SQLite، صف‌های SEC/derivs، سیل WebSocket. راهکار: سهمیه‌ها (بخش 4)، سقف فیدهای بالادستی متمایز، token bucketها، هش ناهمگام، `max_page_count`، محدودیت CPU/حافظه/pids کانتینر.
9. **بن‌شدن از بالادست و مشکلات شرایط استفاده**: 1000 کاربر ضرب در اتصال‌های صرافی باعث بن‌شدن IP سرور می‌شود؛ بازتوزیع داده‌ی Yahoo/CoinGecko/ForexFactory ممکن است شرایط آن‌ها را نقض کند. راهکار: فیدهای multiplex‌شده‌ی مشترک، کش، بودجه به‌ازای هر صرافی، kill switch به‌ازای هر منبع بالادستی، بازبینی مجوز داده پیش از باز کردن ثبت‌نام فراتر از دوستان.
10. **از دست رفتن داده و تعهدات حریم خصوصی**: یک volume ژورنال و تصاویر همه را نگه می‌دارد؛ نبودِ ایمیل یعنی رمز گم‌شده و کدهای بازیابی گم‌شده حساب را از بین می‌برد؛ انتظار export/delete. راهکار: `VACUUM INTO` شبانه + پشتیبان رمزگذاری‌شده‌ی خارج از سرور با بازیابی آزمایش‌شده، نمایش یک‌باره‌ی کدهای بازیابی با تأیید صریح، export و delete کارا، لاگ حداقلی (هش یا کوتاه‌کردن IP بعد از 30 روز)، یک صفحه‌ی کوتاه حریم خصوصی؛ ادمین نمی‌تواند داده‌ی کاربر را بخواند.

(همچنین مراقب باشید: تصاویر آپلودشده‌ی کاربر که از origin برنامه ارائه می‌شوند (`/s/:id`، `/api/media/:id`؛ nosniff و `CSP sandbox` همین حالا هست، بعداً به origin جدا منتقل شود)، و سطح حمله‌ی تجزیه‌گر PDF در `ptr.ts`.)
